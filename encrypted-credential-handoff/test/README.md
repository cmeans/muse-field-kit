# Interop test vectors

Known-answer vectors for the encrypted credential handoff reference protocol (RSA-2048, OAEP-SHA256, MGF1-SHA256, single-line base64).

**The keypair here is a published throwaway.** `test-dummy-priv.pem` protects nothing and must never be used for a real credential. Its presence in the repo is the point: anyone can check an implementation against these vectors.

## Files

- `test-dummy-priv.pem` / `test-dummy-pub.pem` — the dummy keypair.
- `expected.json` — the plaintext payload: `{"svc":"example","username":"dummy-user-Qx7","password":"dummy-pass-K3z9w"}`. The two values differ on purpose, so a swapped mapping fails the test.
- `blob.txt` — `expected.json` encrypted to the dummy public key, base64, one line.
- `expected-check.txt` — the exact expected output of the reference `consume.py --label example --check` on `blob.txt`.
- `run-test.sh` — runs the full check against the reference implementation in this folder.

## Using these vectors for a port or variant

An implementation is interoperable with the reference when:

1. It decrypts `blob.txt` with `test-dummy-priv.pem` to exactly `expected.json` (the `svc` binding check against the label `example` must pass).
2. It encrypts `expected.json` to `test-dummy-pub.pem`, and the reference `consume.py` decrypts the result to the same values (run it with `HANDOFF_PRIVKEY` pointing at a `0600` copy of the dummy key — the reference helper refuses group/other-readable key files, including this published one at its repo permissions).

`run-test.sh` also covers the reference scripts themselves: that `consume.py` passes stdin through to the command, execs the command, directly and through its sh launcher (so a TERM sent to it leaves no credentialed process behind), drops `$HANDOFF_BLOB`, `$HANDOFF_PRIVKEY` and every inherited credential variable (mapped or default name) from the command's environment, hands the command SIGPIPE and SIGXFSZ at their defaults, runs isolated through its sh launcher (a planted `sitecustomize` doesn't run), accepts a blob file with a byte-order mark, and never prints a dummy value itself (the crafted payloads' values carry a marker, `mk-Zq9`, that the leak check looks for too); that `agent-setup.sh --fingerprint` reads `$HANDOFF_PRIVKEY`, accepts OpenSSL 4 and refuses LibreSSL as `consume.py` and `handoff.sh` do, needs `HOME` only for its defaults and `~`, falls back to the same default key as `consume.py` (unset or empty, with a literal `~/` expanded and `~user` refused by both), and agrees with `handoff.sh --fingerprint`, for the dummy key and a freshly generated one; that a 190-byte payload works; and each documented refusal by its exit code and message (purpose mismatch, a payload with no known credential field — `unknown.json` / `blob-unknown.txt` — a payload without `svc`, not JSON or not an object, a non-string or empty credential, a loose or missing key, a key that won't load (a public key), an encrypted key (its passphrase on stdin, and under a terminal), an Ed25519 or P-256 key, an oversized key file, damaged, empty, short or oversized input, no blob or two blob sources, a repeated option, a NUL byte or invalid UTF-8 in a credential, refused `--env` targets and fields (every listed name, in both cases, and every prefix), a blob file that's a FIFO (refused without opening it) or pipe, a device, a missing file or an empty `--blob-file`, a blob path swapped to a FIFO or a terminal between the `stat` and the open (the terminal without becoming the helper's controlling terminal), a private key owned by another user (CI supplies a root-owned copy of the dummy key in `$HANDOFF_TEST_OTHER_OWNER_KEY`; elsewhere the test uses a root-owned owner-only system file such as Fedora's `/etc/shadow`, whose contents are never read, and skips where there is none), no `OPENSSL_*` variable reaching the openssl of any of the three scripts, a blob file that isn't text, openssl missing or not OpenSSL 3/4, `~user` paths, an empty command or one that can't be run, an existing key, an unknown argument, and a 191-byte or misshapen payload). For `handoff.sh`'s key file, it checks that the script holds no key of its own, that `--to NAME` picks `handoff-NAME.pem` beside the script and the paste banner names it (`muse` with no `--to`, options before or after FILE, the file named on stderr, relative to the working directory for a relative path, and beside a symlink rather than its target), that a key file with a byte-order mark, CRLF line endings, or leading or trailing blanks still works, that a near-miss key file name (`handoff_muse.pem`, `handoff-Muse.pem`, `handoff-muse.pem.txt`) is named and a kept old key (`.old`, `.bak`, `~`) isn't, that it encrypts under bash in POSIX mode (`--posix`, `POSIXLY_CORRECT`, `SHELLOPTS=posix`) and from a real file under `/dev/shm`, that FILE after `--` may start with `-`, and its refusals: no key file, a dangling symlink or a symlink loop, a directory, a private key, no key, two keys, a key and a certificate, a damaged key, an EC key, RSA keys of 2052 bits or with e = 3 or 65539 (the same keys `consume.py` and `agent-setup.sh` refuse), a file over 16384 bytes, trailing newlines or NULs included (exactly 16384 is accepted), a key file saved as UTF-16 (either byte order), a script run on stdin, as `/dev/stdin` or `//dev/stdin` or through process substitution with no path of its own, a shell other than bash (zsh, dash, ksh or mksh, whichever is installed), and a bad, empty, non-ASCII or 65-character NAME, a NAME starting with `-`, a missing NAME (or an option in its place), `--to=NAME`, `--to` twice, an unknown option, two FILEs (also both after `--`) and `--fingerprint` with a FILE. It also runs a whole rotation on a copy of the dummy key: `agent-setup.sh --rotate` (the old key kept as `.previous`, the printed public key the new key's), old blobs opening through the previous key with run mode's note to rewrap, `consume.py --rewrap --blob-file` (one blob written over that file in place, the same payload, opening with the current key alone, and which key the old blob was for; nothing written for a blob already for the current key), run mode's note that the current key opened a blob during a rotation, one message for a blob neither key opens, the previous key held to the key checks, `--retire` (refusing without `--yes`, keeping the old key and naming its fingerprint, not confirmed by a caller's `yes=`, `--yes` accepted only right after `--retire` and once, a mistyped `-y`, `y`, `ye`, `-ye`, `yes`, `-yes`, `--y`, `--ye`, `--YES` or `--yes=1` named as the confirmation's misspelling (a KEY only when typed, not from `HANDOFF_PRIVKEY`), a trailing `--yes` named as misplaced, a run without `--yes` still removing a leftover temporary link while keeping `.previous`, and the guard refusals (a symlink, no rotation, a half-done one, a `.previous` that isn't a regular file, the lock, another hard link, absolute and relative, and a failed `find`) run with `--yes`, so the guard, not the missing confirmation, keeps the old key), an interrupted `--rotate` resumed, a failed or short key generation leaving the old key (in `--rotate` and at first setup), a `.previous` copied rather than linked (read by fingerprint) or not a regular file, the lock against two runs (two `--rotate` runs at once, the second refused with the first one's key kept; `--retire` under a held lock; an unwritable key directory reported as that) and the cleanup of a killed run's temporary key, a caller's `$new` or `$lock` deleting nothing, first setup never replacing a key that appears meanwhile, a key directory starting with `-`, a key path starting with `-`, `--rewrap` refused with no rotation under way (or pointed at the previous key), in a half-done rotation (both names holding one key, linked or copied), on a blob neither key opens, with `--blob` or `$HANDOFF_BLOB` instead of a file, and with a blob file under the key's directory (beside the key, in a subdirectory, through a symlink or `..`, or beside a symlinked key path), a rename that fails, a temporary file that doesn't read back, a TERM before and after the rename, an INT during the decrypt and after the write, a HUP inherited as ignored, a blob file changed during the rewrap, the key's directory matched by identity alone after the temporary file is written, a blob for an RSA-4096 key, a key named like a temporary file with a relative or doubled-slash path, the hard-link guard for a path starting with `-`, and the `HANDOFF_LABEL` nesting refusal. It also checks a key path that becomes a directory during generation (first setup and `--rotate`), a TERM mid-generation, a killed setup's temporary key removed by the next, `--retire` removing another link to the old key and refusing while another name holds it, `--rewrap --blob-file` (the file's mode kept, a group-writable file or directory refused and a sticky one allowed, a long multibyte name, a symlinked file rewritten through, a read-only directory leaving it unchanged), `--retire`'s find hint (an absolute path, quoted for a POSIX shell, with an `-inum` form) and a failed `find`, `consume.py` under its launcher with stderr closed, two concatenated blobs, `HANDOFF_KEY_DIR` refused for the key modes, a relative key directory with `CDPATH` set, `chmod` under POSIX option parsing (as BSD's) in first setup and `--rotate`, `--public-key`, and `--help` (also with `HANDOFF_LABEL` set and under `-OO`, and not as an option's value). It runs on Linux; macOS portability of the test itself is issue #3.

Passing both directions is the minimum bar before a port touches a real credential (see `../SETUP.md`).
