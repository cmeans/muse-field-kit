# Changelog — encrypted-credential-handoff

## 0.2.0 — 2026-11-18 — `age` replaces RSA

Version 0.2.0 (#42). **`age` replaces RSA, and a 0.1.0 install sets up again from scratch:** 0.2.0 reads neither 0.1.0's RSA keys nor its blobs, so an install makes a new identity, the user saves its recipient, and each credential is staged again. Closes #37 (whether to adopt OpenSSL CMS for payloads over RSA's 190 bytes: decided against, for `age`; see README, Choosing the suite); see also #39.

PR #42 went through two QA review rounds, with Dev's own pre-QA reviews, and was reviewed by Muse, the agent the folder is written for. It merged only once the author had applied the `QA Approved` label, which only the author applies. The PR records each round's findings and what was fixed or declined, in its body and its review comments; the non-blocking findings left open are #43 and #44. One QA step, typing a payload into a real Windows console with an AltGr keyboard layout, was left to the author and was not run; CI runs `handoff.ps1` with no console. As with 0.1.0, the reviewers were AI agent sessions in the author's setup, plus the author: peer review inside one shop, not a third-party audit.

### Changed

- **`age` replaces RSA-2048 with OAEP-SHA256, for every payload size,** and OpenSSL is dropped from the folder on both sides. The blob is still one line of base64, now of a binary `age` file for one X25519 recipient; the 190-byte limit is gone. README's new "Choosing the suite" says what was compared (OpenSSL CMS, `age` beside RSA, `age` with RSA kept for reading, HPKE, JWE, GPG, libsodium and others), what the probes showed, and the costs accepted (a new dependency, no independent audit found, one main maintainer).
- **Keys and recipients.** The agent's key is an `age` identity, `~/.config/handoff/handoff-identity.txt` by default (mode `0600`, made by `age-keygen`). The user's side holds the agent's recipient, one `age1…` line, in `handoff-<name>.age` beside the script, checked exactly (`age1` and 58 lowercase bech32 characters, so post-quantum, tag and plugin recipients are refused, and `age` itself checks the checksum before any secret is read); a file holding an identity is refused with the message to delete it now. The identity check compares the whole recipient, which is short enough to read in full: README and SETUP say "recipient" where they said "fingerprint", and `--fingerprint` (`-Fingerprint` on Windows) now prints the recipient. `agent-setup.sh --rotate` and `--retire` work as before, with identities.
- **The header check (an allowlist).** Before `age` runs, `consume.py` decodes the blob and reads its header: the first line must be `age-encryption.org/v1`, the header must name exactly one X25519 recipient, and the only other stanzas accepted are the random `-grease` ones rage adds. A passphrase (scrypt), plugin, post-quantum, SSH or unknown stanza, a blob for two X25519 recipients, one with only grease stanzas, and an armored blob are each refused with a fixed message. `age` runs with an environment of `PATH` alone, never with `-p`, `-j` or a passphrase, and only with the identity at the key path, which must hold exactly one plain `age` secret key (a plugin or post-quantum identity is refused). There is **no minimum `age` version**: the header check closes the one behavior that differed (`age` 1.0.0 asks the terminal for a passphrase when given a passphrase blob).
- **The blob limit:** `consume.py` accepts at most 65,536 base64 characters (`MAX_BLOB_FILE`), and `handoff.sh` and `handoff.ps1` send at most 48,696 bytes of payload (`MAX_PAYLOAD`), with room for a rage grease stanza; README "Limits" has the arithmetic. Line breaks and blanks in a blob don't count toward the cap, from a file as from `--blob`; a `--blob-file` may hold up to 131,072 characters as read (`MAX_BLOB_FILE_RAW`), line breaks included, so a blob at the cap saved wrapped still opens. The cap was measured on the stores: each of five stores tested on Muse (2026-11-17) carried a 64,000-character blob, so none limited it. The chat path carried one too: an 8,000-character and a 64,000-character blob, which the author pasted into a chat with Muse on 2026-11-17, each arrived at exactly that length, and `consume.py --check` passed on both, so the cap stays.
- **`jq` 1.6 or newer is required** by `handoff.sh`, which now refuses to run without it instead of warning and skipping the payload checks: building a `private_key` payload needs `jq --rawfile`.
- **`handoff.sh` and `handoff.ps1` refuse every payload `consume.py` would refuse for its shape or fields,** before anything is encrypted; only the label match is left to `consume.py`. Bytes that aren't UTF-8 (a Latin-1 file, say) and a `\uD800`–`\uDFFF` escape that isn't half of a pair get the JSON message (`handoff.sh` now checks both, as `handoff.ps1` did), as does a raw control byte, a raw NUL included (in a string, between tokens, or in a UTF-16 file without a byte-order mark: `handoff.sh` used to drop a raw NUL, as bash's `$(...)` does, and encrypt the shortened value), and a leading UTF-8 byte-order mark is dropped. Both scripts now also refuse, each with its own message, a NUL (`\u0000`) in any value, an empty credential field (an empty unknown field is still ignored, as `consume.py` ignores it), and a payload with no known credential field; a repeated key counts the last one, as in `consume.py`. `test/payload-cases.json`, which both test suites read, has a case for each.
- **0.1.0 files are named, not misread:** an RSA key at the key path is refused by `consume.py` and `agent-setup.sh` with a message that 0.2.0 uses `age` and a 0.1.0 install sets up again; a `handoff-<name>.pem` beside the script without a `.age` file gets the same message from `handoff.sh` and `handoff.ps1`; a blob the size of a 0.1.0 RSA blob gets the same hint.
- **SETUP:** prerequisites without OpenSSL (`age` and `age-keygen`, the current release recommended; Python 3.7 or later; on the user's side `jq` 1.6 or newer for `handoff.sh`, and only `age` for `handoff.ps1` on Windows), and work from a release tag. Step 1 ends with `./agent-setup.sh --check-setup` before any key is made. Step 3: the agent never sends the script; it names the release and the user's platform's commands from README "Getting the scripts", gives only the recipient through chat, and asks for the user's own setup check result before the recipient comparison. Stop conditions include a `FAIL` line and the header check's refusals; the record list adds the release, the `age` version, the setup checks' results, the user's platform and script, and each label's payload fields. Platform: the agent's side runs on Linux and macOS (Homebrew `age`, its `bin` directory in each wrapper's `PATH=` line), and not on Windows.
- **README:** "Installing age" per platform (distribution packages, with the versions they carry; Homebrew; winget; phones, marked untested: Termux, iSH, third-party apps), how to run `handoff.ps1` under Windows' execution policy, and checking a downloaded `age` binary with its Sigsum proof. "Getting the scripts" (below). "Platform" says what CI runs on each system. "Status" says what 0.2.0 has and hasn't yet run in the field.
- **`agent-setup.sh` checks its shell, as `handoff.sh` does:** run by zsh or `sh`, it says to use bash (0.1.0 failed with `command not found: compgen` and a misleading refusal), and bash in POSIX mode (macOS's `sh`, or with `POSIXLY_CORRECT` set) leaves that mode first.
- **Root `SECURITY.md`:** 0.2.x is the supported version; 0.1.x is no longer supported, since 0.2.0 replaced its cryptography.
- **Changes go upstream as issues.** README's "Variations" and SETUP's mechanism-change rule offered changes "as an issue or pull request"; pull requests in this repository are now opened by its collaborators only, so both say to open an issue, pointing to the repository's new `CONTRIBUTING.md`.

### Added

- **Three payload fields:** `private_key` (a PEM or other multi-line secret, injected byte for byte as `SERVICE_PRIVATE_KEY`), and `app_id` and `installation_id` (`SERVICE_APP_ID`, `SERVICE_INSTALLATION_ID`), which a GitHub App needs beside its key. Each stands alone and maps with `--env` like the others. This is a payload-schema change (SETUP's mechanism-change list). README "Payloads" shows building a `private_key` payload from a key file with `jq --rawfile` (or, on Windows, `[IO.File]::ReadAllText` and `ConvertTo-Json -Compress`) piped into the script, with nothing written to disk and no secret on a command line.
- **`handoff.ps1`, the user's side on Windows:** the twin of `handoff.sh` (the same recipient file, rules and messages), for Windows PowerShell 5.1 and PowerShell 7, needing `age.exe` and nothing else (no bash, Git or `jq`). It reads the payload with echo off and outside PowerShell's history, or from `-File` or the pipeline, and checks it with a JSON reader of its own that behaves the same on both editions.
- **Release files.** Each tagged release carries `handoff.sh`, `handoff.ps1` and `SHA256SUMS`, byte for byte the folder's files at the tag, each script with a build-provenance attestation, published by a release workflow from a `v*` tag on `main`, with this file's section for the version as the release notes. README "Getting the scripts" gives the download and check commands for each platform (`sha256sum` or `shasum`, `Get-FileHash` and `Unblock-File`, `gh attestation verify`, or a `git clone` of the tag), and says what the checksum does and doesn't prove; CI runs README's own check commands on the built files.
- **`--check-setup`** (`handoff.sh`, `agent-setup.sh`) and **`-CheckSetup`** (`handoff.ps1`): a functional compatibility check on each machine. It runs the tools instead of comparing version strings: `age` and `age-keygen` start, a round trip through a throwaway identity (made in a private temporary directory, removed on every exit, including an interrupt) encrypts and decrypts a non-ASCII payload unchanged, the blob's header is exactly one `X25519` stanza (the rule `consume.py` applies), and the blob survives `base64`. `handoff.sh` also checks `jq` 1.6 or newer and `jq --rawfile`; `agent-setup.sh` checks `python3` 3.7 or newer and runs the round trip through `consume.py --check` itself. The saved recipient file (or, on the agent side, the key) is checked if it exists; a missing one is `INFO`, and `HANDOFF_KEY_DIR` without `HANDOFF_PRIVKEY` is a `FAIL` naming `HANDOFF_PRIVKEY`, as `--fingerprint` refuses it. `age-keygen` is not needed on the user side: without it the round trip is encrypt-only. Output is one `PASS`, `INFO` or `FAIL` line per check on stdout and nothing else; the exit status is 1 if any line is `FAIL`. It reads no stdin and never prints the test payload.
- **Tests and CI on three systems.** Known-answer vectors from Go `age` and from rage (with a grease stanza), and one refusal vector per header case (`test/vectors/`). CI runs on Linux (the whole suite against the packaged `age` and the 1.3.2 release binary, pinned by SHA-256 and checked once against its Sigsum proof; the agent's side against 1.0.0 and 1.1.1 built from source), on macOS (the whole suite with Homebrew's `age` and `jq`), and on Windows (`test/run-test.ps1` under Windows PowerShell 5.1 and PowerShell 7, with its blobs then opened on Linux by `consume.py`). A skipped check fails the run. For the macOS job (#3 asked for one), the suite reads file modes, owners and inodes with BSD `stat -f` where GNU `stat -c` isn't there, compares `wc` counts as numbers (BSD `wc` pads them), bounds its waits with `gtimeout` or nothing where there is no `timeout`, runs BSD `script` in its own form, and expects `--to Muse` to open `handoff-muse.age` on a case-insensitive file system (APFS by default); `handoff.sh` reports a payload's size without the padding. On the pull request every job passed, on Linux, macOS and Windows.

### Removed

- Every `openssl` call, the OpenSSL 3/4 gate and the LibreSSL refusal, the macOS `openssl@3` `PATH` lines, the RSA key and blob vectors, and the 190-byte limit and its tests.

## 0.1.0 — 2026-11-16 — first publication

The folder's first public version. Nothing here has been released before, so this entry describes what ships, not a sequence of changes. (Renamed before publication from "blind-RSA credential handoff": "blind RSA" names a different, standardized technique.)

Before its first commit, the folder had a structural review and a line-level script review, with findings reproduced. PR #1 and PR #7 (the rotation tooling) then went through a cold read and several QA review rounds, each with Dev's own pre-QA reviews, and each pre-release PR after them (#12, #17, #20, #24, #29 and #34) had QA review rounds with Dev's pre-QA reviews. Every one was also reviewed by Muse, the agent the folder is written for, and merged only once the author had applied the `QA Approved` label, which only the author applies. Each PR records its rounds' findings and what was fixed or declined, in its body and its review comments. The reviewers were AI agent sessions in the author's setup, plus the author: peer review inside one shop, not a third-party audit.

Before publication, Muse also ran it live: the published `consume.py` and wrappers on two of its production labels, one complete routine rotation on them (rotate, rewrap, last pass and retire, 2026-11-14), and each of the five stores in the table under README's "Choosing a store" end to end with a dummy blob (2026-11-14).

### Added

**The pattern** (README.md)

- **Threat model**, including what the pattern does not defend against: host trust, the agent account, no sender authentication, no forward secrecy under key compromise, the helper as a decryption oracle (execute access to the helper is read access to every staged credential), writers to the store (a store writer can plant a blob for a label; signed blobs would close it), and the unattended-fetch credential.
- **Ten invariants**: one-way delivery, careful ciphertext storage, plaintext never in a model's context, never on the agent's disk, mandatory key/ciphertext separation, identity verification, provenance (stage only blobs the user pastes), purpose binding (`svc`), controlled egress and key confinement.
- **Choosing a store** (issue #30): what step 4's store must be, as six requirements (R1 separation from the key, with no local mirror or cache; R2 store, fetch and replace by label, and delete; R3 private; R4 a fetch with no secret on the agent's machine, through the platform's own session, or the stated weaker form with a scoped credential; R5 a ciphertext-only path to the helper; R6 checkable and recorded), plus what a store keeps after a replace and what else its access reaches. For Muse, dated November 2026: a stock Muse has no off-disk store until one is connected, and its memory files are never one; the stores tested on Muse on 2026-11-14 (a dedicated Upstash Redis database through a custom connection, Google Drive, Dropbox, Notion, and a shared remote memory service) in a table with their history, delete and reach, ranked, with the limited forms (an on-VM fetch credential, `/dev/shm`, 48-hour file links) and the non-stores. The provider-side setup is stated as what the store must be, linking the provider's own documentation, not its console steps. What Allow and Allow Always would mean for a store's connection (none appeared when four of the five stores were staged, Dropbox's staging needed a one-time grant, and the fetches weren't asked about, so whether one can hold up a wrapper's fetch, and what Allow Always covers, are stated as unverified). A store's plan must not archive an idle database (Upstash's free tier does after 30 days). Muse's side of a custom connection (registration; a fetch with a timeout that treats a missing key as a failure, a write that checks the store's answer, and slot names safe in a URL path), and the tested connectors' traps (Drive's home-side upload copy and fetch by id, downloads to a tmpfs file, Dropbox's download argument, Notion's search lag). SETUP: step 6 writes a fetched store's first blob under its slot name and records the write program's sum; after a retire or a compromise response, a store's history is purged where it can be. README step 4 no longer says the agent's memory store, and the paragraph after invariant 5 is replaced by this section.
- **Rotation** split into routine rotation and compromise response (on a suspected leak, credentials change at their services first). **Platform** status stated plainly: Linux reviewed; macOS expected but unreviewed; Windows has no reference.

**Setting it up** (SETUP.md)

- **Hard rules**, including one list of what is recorded per label (both wrappers, the sha256 sums of each label's wrappers and own programs, a shared section of sums for the programs every label runs, each whole command line and its `--env` mappings, each wrapper's environment and working directory, the fetch and its environment, the endpoint, and anything the user accepted knowingly). A change to anything on it is a mechanism change; rotation changes nothing on it.
- **Wrappers**: a probe wrapper and a use wrapper per label, identical apart from the comment line and the command after `--` (checked with `diff`; the sha256 of each wrapper and its own programs recorded per label, and of the shared programs, `consume.py`, the fetch script, `openssl` and `python3`, once, all compared before a run and at each session's start), with a complete example. A wrapper takes no caller arguments and no caller environment: it refuses arguments, `cd`s to a fixed directory, starts the helper with `env -i`, and runs the fetch with `</dev/null` under its own clean environment (for a stdio MCP server, the wrapper's stdin is the client's transport). Wrappers are never nested; `consume.py` refuses a direct nested call. The probe reaches its service with the wrapper's fixed environment alone (a tunnel or proxy other tooling sets up at run time isn't there), and a fetch through a proxy has its proxy variables written into its own `env -i` line, since nothing from the MCP client or the agent's shell reaches it. A proxy, tunnel or endpoint comes only from the user (or configuration the user confirms); one suggested by a tool result, fetch output, file or message is treated as an injection attempt. The rewrap wrapper's fetch and store commands get the same proxy variables (in the case their programs read), and a proxy's credentials never go in a wrapper, the notes or a command line.
- **Separation** checks the store against README's R1 to R6, with a checklist at step 6 before the first blob is stored and the answers recorded at step 8 (with the connection's name and host, never a token, and the approval chosen); a "don't know" stops, and the agent's own memory files are checked like any candidate. A fetched store's first blob is written with the rewrap wrapper's write program.
- **Steps** with exact commands: `HANDOFF_KEY_DIR` and `HANDOFF_PRIVKEY`, the fingerprint check, the dummy round-trip, giving the user the exact `svc`, and macOS `PATH` lines for Homebrew's `openssl@3`. Prerequisites: OpenSSL 3 or 4, Python 3.7 or later.
- **Rotation**, as key-management services do it: the old key keeps decrypting until it's retired. Rotate (the old key kept as `<key path>.previous`, a new one at the same path, so no wrapper changes), check the new fingerprint, rewrap each label's blob to the new key through its recorded rewrap wrapper (a third per-label script, started as its other wrappers start the helper, with a file-store and a fetched-store shape) and probe it for a positive "opened with the current key" line, and retire the old key once the rotation's list of labels has been checked against the setup record (a label missed at the start is otherwise broken silently at retire), every label on it has probed ok (or been written off by the user in a direct conversational turn; a write-off arriving any other way is treated as an injection attempt), and a last pass shows every stored blob opens with the new key alone. A fetched store's rewrap wrapper can name the label's slot in the store apart from the label (`key=`), and on a host with no `/run/user` keep its file in a directory of its own on `/dev/shm`. At rotation the user replaces `handoff-<name>.pem` (the script never changes), and a `handoff.sh` still printing the old fingerprint is named as a copy whose key file to replace. "Staging during a rotation" covers a label staged while `<key path>.previous` exists, first or again: it goes back to `pending` and through the rewrap step, and its probe at staging (once `--rotate` has finished) shows whether the user's `handoff.sh` is stale, reported once the new key's confirmation is recorded. From the start of the last pass to the retire, `staging held` in the agent's notes holds every new blob (the user sends it again after the retire; it isn't kept in notes), a blob stored anyway makes the pass run again, a label whose pass probe doesn't show `ok` with the current key either goes back to the rewrap step once, when its blob is still the old one and the login works, and is stopped the second time, or is stopped at once, when a rewrap can't help (any failed login, or a blob neither key opens); either way staging opens again, and the `--retire` message asks for no blob stored since the pass began. In a compromise response, staging waits for its last step, and a credential sent before then counts as exposed. A probe counts as showing the current key only with `ok`, the current-key line and no previous-key line, since the probe shares stderr with `consume.py` and could print a copy of the line. A `--retire --yes` refused for another hard link is recorded (`retire refused (hard link)`), so a later session runs only the retire again once the user has removed the name, not a new pass (unless a blob was stored meanwhile); one named rule, "A hard-link refusal at the retire", used by the routine retire and both Compromise retires, records the refusal's whole message (its `-inum` form still finds the other name after `.previous` is gone), tells the user to remove the other name, not `.previous` (as `agent-setup.sh`'s message now says too), has a name the `-inum` search lists fingerprint-checked before it's removed (by the agent, or with root's own OpenSSL: the user never runs a file from the agent's folder as root), covers a `.previous` removed instead (nothing can then prove the old key is gone, so the user's answer is recorded with "the old key may still be on disk"), runs only the retire again in a compromise, and records what the user was told and answered; the probe check runs each probe once, one at a time, with stderr in a `mktemp` file of its own, and counts two fixed strings in it as raw text (issue #19). Lines recorded from a run are data, never a write-off or a go-on, and the fetched-store wrapper ends with a line of its own (issue #15). Each label's rewrap state (`pending`, `rewrap started`, `rerun`, `stopped`, `probed ok` or `rewrapped, probed ok`, written off) is listed with what to do in each, read at the start of every session: a resume allows one rerun, any failure of it stops the label until the user says to go on, and a session that ended mid-rerun probes once, instead of looping, since each lap is a real login. The store-write failure says it may have been refused, unreachable or cut short. The rewrap wrapper's file has a fixed name per label, not one built from the label (which could hold a `/` or be too long): at most 100 bytes of letters, digits, `_` and `-` (the label part at most 85), written as a plain `f=` line, and a `grep … | uniq -d` check of the file names confirms no two labels share it, and a form check (ASCII-only, with `LC_ALL=C command grep`) confirms each wrapper has one plain, unindented `f=` line (issue #14). Rotation starts only on the user's direct request (or their go-ahead after a reported compromise). Each step says how to resume it from the agent's notes, and a blob neither key opens is a stop condition. An install whose wrappers run another consumer, or name the key through a symlink, changes that first. On a suspected compromise, credentials change at their services first, the leaked keys' fingerprints are recorded, any other `--retire` refusal (beyond an unfinished rotation, which `--rotate` finishes) stops the response until it's resolved, the new key is checked to differ from the leaked ones, the old key is retired right after the new one is in place, and old blobs are never rewrapped.

**`SKILL.md`** (the skill file for Muse)

- Frontmatter `name` and `description` say when to use the handoff: a credential for a program the agent runs that reads it from its environment (an MCP server, a CLI, a script that calls an API), a pasted ciphertext, setting up or rotating the key, checking its fingerprint, a suspected leak, and a user offering to paste a plaintext secret (declined). A "Not for" note excludes website sign-in, file-shaped secrets, config-file or stdin delivery, and any credential the agent would have to read itself. The body routes each request to its step in `SETUP.md`, which stays the authority (on any difference, `SETUP.md` is followed and the user told), says to check the agent's notes for an existing setup first and otherwise clone the repository, and to use nothing beside the skill file (README's setup prompt asks Muse to install the folder as a skill, since Muse finds a skill only once it's installed; `SETUP.md`'s hard rule "Installed as a skill" governs that copy, and SETUP defines "this folder" as the clone's), and repeats five rules from `SETUP.md` that hold from the start: no plaintext asked for, printed or written to disk; the private key never read; only blobs the user pastes in a direct turn staged; each label run only through its recorded wrappers; and the stop conditions.

**`handoff.sh`** (the user's side)

- Encrypts with RSA-2048, OAEP-SHA256, MGF1-SHA256; prints only the base64 ciphertext on stdout. Reads the payload with echo off, or from a file or pipe; checks it's a single JSON object with a string `svc` and string values (with `jq`), and at most 190 bytes.
- **The key lives beside the script, not in it** (issue #23): `handoff.sh` reads the agent's public key from `handoff-<name>.pem` in its own directory (the directory in the path it was run by, not resolved through a symlink), with `--to NAME` choosing the recipient (default `muse`; letters, digits, `_` and `-`, at most 64, not starting with `-`). There's no key in the script and no fallback: a missing key file means no ciphertext. A key file that isn't a regular file, is over 16384 bytes, or isn't exactly one RSA-2048 public key with e = 65537 is refused, and one holding a private key is refused with a message to delete it at once. A symlink that doesn't resolve is named as one, a script run without a path of its own (on stdin, through `bash -c`, or from a descriptor such as `bash <(...)` or `/dev/stdin`, checked after resolving the path) is told to save the script to a file and run that file, since there's no directory to find the key in, and a copy with a UTF-8 byte-order mark, CRLF line endings, or leading or trailing blanks still reads; one saved as UTF-16 is named as that, and a near miss beside the script, from a short allow-list (a `_` or `.` in place of the `-`, another case, or an extra `.txt` or `.pem`), is named, quoted, with a check to make before renaming it (or, when only NAME's case differs, the `--to` it probably meant); a kept old key under any other name isn't offered. Run by zsh, it says to use bash; bash in POSIX mode (macOS's `sh`, or with `POSIXLY_CORRECT` set) leaves it, so the encrypt step works there too. Options may come before or after FILE. Every run names the key file beside the fingerprint (on stderr for `--fingerprint`), and the paste banner names the recipient. The key file is read once, with its size checked on what was read (trailing newlines and NULs included). A rotation replaces the key file; the script never changes.
- The fingerprint fails closed on a damaged key. Requires OpenSSL 3 or 4 (refuses LibreSSL, with a `PATH` hint), and drops the caller's `OPENSSL_*` variables.

**`agent-setup.sh`** (the agent's side)

- Generates the keypair (mode 600, a 700 directory it creates; it refuses to overwrite a key or to treat an unknown argument as "generate"). `--fingerprint [KEY]` (and `--public-key [KEY]`, which also prints the public key, for a resumed setup or rotation) reads `KEY`, else `$HANDOFF_PRIVKEY`, else the same default key `consume.py` uses, and names the file it read; it refuses an encrypted key, a key that isn't RSA-2048, and a file over 16384 bytes.
- `--rotate [KEY]` keeps the key as `KEY.previous` (a hard link, so it's never replaced) and renames a new key over `KEY`, printing the new public key and fingerprint; the new key is checked before it replaces anything, so a failed or short key generation leaves the old key in place. While a rotation is under way it rotates nothing and shows the new key's public key and fingerprint again (exit 0), and a re-run after an interruption finishes it; which state a rotation is in is read from the keys' fingerprints. `--retire --yes [KEY]` deletes `KEY.previous` (and a temporary file that is another link to it), refusing when there's none, the rotation didn't finish, or the old key has another hard link. Without `--yes`, after those checks, it keeps the old key (removing only such a leftover temporary link to it): it names the old key and its fingerprint, says a blob still made for it never opens again, and exits 1, since the script can't tell whether some label's blob still needs the old key (issue #4). `HANDOFF_KEY_DIR` without `HANDOFF_PRIVKEY` is refused in these modes, a misordered flag isn't taken as KEY, and an interrupted `--rotate` says how to finish. Both refuse a symlinked key path and a `.previous` that isn't a regular file, take a lock so only one runs at a time per key directory, and treat a key path starting with `-` as a path. `--rotate` removes a temporary key a killed run left. A TERM, HUP or INT during `--rotate` or first-time generation leaves no temporary private key behind.
- First-time generation writes the key to a temporary file and checks it before linking it into place, so a failed or short key generation (genpkey can exit 0 after a short write) leaves nothing at the key path, and a key that appeared meanwhile is never replaced (the key directory needs hard links). A failing DER export is reported as unreadable, not as another key type, and paths starting with `-` are paths. A TERM, HUP or INT during generation leaves no temporary private key behind.
- One `~/` rule shared with `consume.py` (`~user` refused), `HOME` needed only for the defaults and `~`, the same OpenSSL 3/4 gate, and `OPENSSL_*` dropped.

**`consume.py`** (the consume helper)

- Loads the key on its own first, never prompting for a passphrase, and checks it's an RSA-2048 key with e = 65537 (a key that won't load, an encrypted one, another key type or size, or a file over 16384 bytes is reported as such, with openssl's readable reason, cut to 300 characters), then decrypts in memory (a failed decrypt names the likely cause, a blob made for another key or a damaged one, and says to stop and report it), checks `svc` against `--label`, and **execs** the command with the credentials in its environment (a TERM to the helper reaches the command; no credentialed child is left behind). Run as `./consume.py`, it re-runs itself as `python3 -I` through a two-line sh launcher (no `env -S`, which BusyBox lacks).
- Prints nothing derived from the payload. `--check` shows field names and lengths, for the dummy round-trip only.
- **Rotation:** a blob the current key can't open is tried with `<key path>.previous`, held to the same key checks; a blob neither key opens (or the current key, with no rotation under way) gets one fixed message, naming the key files it tried but without openssl's reason, saying to stop and report it. In run mode, a blob opened by the previous key gets a note to rewrap it. `--rewrap` runs only during a rotation that has a new key in place (refused with no `<key path>.previous`, or with one holding the current key, so a wrong `HANDOFF_PRIVKEY` or a half-done `--rotate` can't make a label look done), rewrites its `--blob-file` in place (required; `--blob` and `$HANDOFF_BLOB` are refused): the same payload, encrypted to the current key and checked to open with it to the same bytes, written atomically (a synced temporary file beside it, read back, then renamed; a failure, or a TERM, HUP or INT not inherited as ignored, before the rename leaves the file as it was, and one after it is reported as the file holding the new blob; a file changed meanwhile, such as a blob staged during the rewrap, is left as it is), keeping its mode and, where allowed, its group. It writes nothing for a blob already for the current key, refuses a blob file that resolves (symlinks and `..` followed) to anywhere under the key's directory, compared by path and by identity (a bind mount or another case of it), or that is group- or world-writable or in such a directory without the sticky bit (the message gives the `chmod`; checked for an already-current blob too), and its stderr line names the file and the key file the old blob was for; it takes no command and no `--env`. A blob that is several concatenated is named as that. During a rotation, run mode notes a blob the current key opened too, so a probe checks for a line that's there. A closed or read-only stdout or stderr is replaced with `/dev/null` at startup, so a note never fails at flush or lands on a stdio server's stdout. `--help` prints the usage, read in option positions only.
- **Nesting:** the command gets `HANDOFF_LABEL` (the label), and the helper refuses to start when `HANDOFF_LABEL` is set, so a command one call started can't run `consume.py` again directly by accident. It's an accident guard, not a boundary (a command can unset it), and a wrapper's `env -i` drops it along with the outer credentials: nesting through a wrapper is SETUP's rule to keep. `HANDOFF_LABEL` is on the refused `--env` list.
- **Environment:** the default `SERVICE_*` names and its own mappings are removed from what it inherits before the payload's values go in, along with `$HANDOFF_BLOB` and `$HANDOFF_PRIVKEY`. `--env` maps only the known fields, each once, and refuses targets that aren't plain names or that change what the command runs or where it connects (a partial list, compared case-insensitively). `OPENSSL_*` is stripped from its own openssl calls.
- **Input:** exactly one blob source; `--label`, `--blob`, `--blob-file`, `--check` and `--rewrap` at most once each; a blob file must be a regular file (checked before opening, opened non-blocking, rechecked); empty, wrong-length or oversized blobs, empty, NUL or non-UTF-8 values, and non-OpenSSL-3/4 openssl are clean refusals, never tracebacks.

**Tests and CI**

- `test/run-test.sh`: a known-answer decrypt vector and an encrypt round trip through `consume.py` (OAEP is randomized), the exec and TERM behavior through both entry points, leak checks on the helper's own output (every crafted value carries a marker), fingerprint agreement across the scripts, the 190/191-byte boundary, and every documented refusal by exit code and message, including a key owned by another user (from a root-owned owner-only file; skipped where there is none) and a blob file swapped to a terminal after its check (refused without taking a controlling terminal). It needs only bash, python3, openssl and jq, and runs without execute bits. The PR #1 rounds checked the suite with mutation runs kept outside the repo, and issue #2 brings mutation testing in; the survivors those runs found were fixed by new tests.
- CI runs the execute-bit and line-ending checks, shellcheck, a parse of the scripts under bash 3.2 (macOS's `/bin/bash`), `ruff check` and the suite, gives the suite a root-owned key file for the key-owner refusal, and fails if the suite skips any check. `.gitattributes` keeps scripts and vectors LF.
